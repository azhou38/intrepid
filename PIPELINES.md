# Agent pipelines for curation

Roles and order for improving destinations, spots, photos and copy in the background (as scheduled cloud agents that open pull requests). **The rules live in the existing guides — do not restate them here:**

- coverage, placement, ranking, recall, coordinates → `COVERAGE.md`
- names, fields, voice → `WRITING.md`
- every photo, the pre-filter, headers, why-visit and spot photos, the header workflow and manifest → `IMAGES.md`

## Shared conventions
- **Unit of work:** one destination for imagery and writing; one **region** for coverage (`COVERAGE.md` → "The unit is a region"), so places between destinations are searched with the same effort as places inside them.
- **Batches of 5.** One branch and one pull request per batch of **5 destinations** (coverage: one region per pull request), with **one commit per destination** so any single destination can be reverted on its own. Never merge: the agents only open pull requests.
- **Pull request mechanics (verified by the cloud probe):** `git push` of a branch works; `gh pr create` does **not** (GitHub's GraphQL API is blocked in cloud sessions), so open the PR with the REST API: `gh api repos/azhou38/intrepid/pulls -f title=… -f head=<branch> -f base=main -f body=…`, then assign it to `azhou38` through the REST API so GitHub notifies the owner.
- **Title and body:** the title names the destinations ("Wellington, Napier, Rotorua, …: photos and copy"); the body carries the evidence (sources, contact sheets, coverage table).
- **Notify on completion:** send a push notification ("N destinations updated, PR ready") with the pull request link.
- **One writer per file:** each agent writes only its own output file; a single merge step edits `src/data/*`. No shared scratch folders.
- **Evidence on every PR:** sources for facts, before/after contact sheets for photos, an evidence table for coverage.
- **Scripts do the objective checks:** `npx tsc --noEmit`, `scripts/check-destination-headers.ts`, `scripts/audit-spot-coordinates.ts`, `scripts/build-image-manifest.ts` (slow; its own job).
- **Backlog order:** weakest first — for coverage, regions that have never had a region pass come before everything else; then archival or reused photos, generic bios, ambiguous names, few spots, benchmark failures.

## Pipeline A — coverage (destinations, spots, orphans)
Runs **per region** and keeps inclusion separate from placement, so a place's chance of getting in does not depend on whether a destination surrounds it (`COVERAGE.md` → "Finding what is missing").
1. **Enumerator** — the region's candidates from sources, across all of its land, with each candidate's score (`views`, `counted_sources`) and coordinates. It does not look at our destinations.
2. **Scored filter (script)** — `scripts/curation/score-filter.ts` decides the clear cases from the score and the name: a strong score with no part-of or feature-name signal is kept; an event, civic building, vehicle, minor memorial, accommodation, or a place with no counted source *and* little interest is rejected. Everything else is the marginal band. Every script decision is listed (`auto-decided.json`) in the report, and a deterministic sample of them (`audit.json`) is re-decided blind by the judge.
3. **Coverage judge (one agent)** — reads only the marginal band (plus the audit sample) and gives each entry a verdict on "What qualifies" alone, with the skeptic's source check and objection built in. It is blind to placement. `merge-verdicts.ts` joins script and judge verdicts into `verdicts.json` and `skeptic.json`; if the judge disagrees with more than 1 in 10 of the audited script decisions, the script's rules do not fit the region and the judge runs on every candidate instead (the full path). Silence is not allowed. Photos are Lens's job, not Atlas's.
4. **Proposer** — only now places each kept candidate: a spot of a destination, a standalone spot, or a new destination (`COVERAGE.md` → "Where a spot goes"). A kept place is never dropped here for want of a home.
5. **Verifier (script + report)** — names, ids, spans, coordinate audit, and the **fairness report** (`COVERAGE.md` → step 5): lowest-scoring kept spots, higher-scoring candidates left out with their reasons, the inside/standalone split, the strongest outsiders. The run is accepted only if every strong outsider left out has a concrete reason.
Benchmark: the full list in `COVERAGE.md` → "Finding what is missing" (Red Rocks, Kapiti Island, Lake Coleridge, Sumner Beach, Godley Head, Lyttelton, Birdlings Flat, Paradise, Hump Ridge Track, St Kilda Beach, Ohakune Carrot; Ninety Mile Beach standalone, not under Cape Reinga; Walter Peak High Country Farm in place of TSS Earnslaw; Pipiriki to review).
   - The judge must not hold back second-tier stops (a beach, headland or harbour town that one guide names); its job is to reject the rarely visited and the vehicle-as-spot.
   - Output per region in `curation/<branch>/region-<id>/`: `candidates.json`, `verdicts.auto.json`, `marginal.json`, `auto-decided.json`, `audit.json`, `judged.json`, `audited.json`, `verdicts.json`, `skeptic.json`, `placement.json`, `fairness.json`. `scripts/curation-backlog.ts` counts a region as covered once its `fairness.json` is committed.

## Pipeline B — imagery
**Every photo that goes into the app is judged by Lens, including the photos of new spots.** A photo proposed by Atlas (the enumerator, the skeptic or the proposer) is a candidate, not an accepted photo: the new spot goes in, but its photo is applied only after the image-judge has looked at it against the four checks, the crop and the brightness floor (`photo_verdict: accept`). `apply-region.py` does not apply a photo without that verdict. Turangi, a town, shipped with a photo of a riverbank because new-spot photos were applied from the skeptic's pick unjudged; the judge is where "the photo shows the named thing" is enforced.
1. **Pre-filter and proof (scripts)** — `IMAGES.md` → "Automatic pre-filter", over every photo in the app; then `scripts/curation/photo-prove.py` on each group's `task.json`: a Commons photo geotagged within 300 m of the spot's pin, with a distinctive word of the spot's name in its title, description or categories, no excluded category, dated 2000 or later, wide enough and in colour is **proven** and needs no judge (every 8th proven slot is still sent to the judge blind, as an audit; if the judge rejects any, the group is rerun with everything judged). A hard failure goes straight to search. What the script cannot prove (no geotag, name not in the text, a non-Commons photo, a header or why-visit photo) goes to the judge.
2. **Candidates (script), then searcher for the gaps** — `scripts/curation/gather-photo-candidates.py <group-dir>` searches every slot by name **and by location**: the Wikipedia lead image and Commons name and geo searches, and, at the same time, Google Images through Apify (one call per group, 50 results per slot, about $0.005 a slot; `APIFY_TOKEN` in `.env.local`). Google hits that are Commons files go through the Commons checks; the rest are kept only from hosts not excluded in `scripts/curation/photo-sources.json`, labelled "official photo, used with permission" for the tourism and parks sites listed there and "web photo, permission not confirmed" otherwise. Both searches go on one contact sheet per slot, ranked by source (lead image, named Commons photos, official sites, geotag-only Commons photos, other sites). Add a new region's tourism and parks sites to `photo-sources.json` before its run. It then filters, de-duplicates and downloads the candidates and draws a contact sheet per slot ("Lean runs"). The image-searcher (Haiku) is sent only to slots the script found **nothing** for, slots whose candidates the first judge rejected, and sources the script could not reach. It searches the official tiers (tourism boards, parks agencies, operators), Commons categories and the browser step.
   - **Every empty or rejected slot, no cutoff:** never limit the search to "headline" slots to save tokens (`IMAGES.md` → "When Commons has no suitable photo"). A `confirm` slot the judge rejects is queued like an empty one.
   - Commons first (its licence data is clean and the app hot-links its thumbnails); prefer Featured, Quality and Valued images.
   - **Non-Commons search is mandatory, not optional:** every rejected or empty slot gets the fallback below in the same run, and the passing photo is downloaded, committed and registered (`IMAGES.md` → "When Commons has no suitable photo"). Queue *all* rejects (`scripts/curation/build-search-queue.py`), not just the first groups judged.
   - **Browser step (standard):** when tiers 1-3 find nothing and the official or operator pages were blocked to scripts, harvest them in the in-app browser (`IMAGES.md` → tier 4) before reporting the slot missing. Cloud routines cannot: they report those slots as "needs a browser".
   - **Fallback when Commons has nothing usable:** use the order in `IMAGES.md` → "When Commons has no suitable photo" (openly licensed first, ND included: DOC images labelled Creative Commons; then official photos from tourism and parks organisations, used with the owner's permission; other official photos, flagged; blogs last). A spot is never dropped or left with a wrong photo for want of a Commons file.
   - Unsplash/Pexels only for headline destinations (their location tags are unreliable); Google Places photos are out (terms).
   - Cloud runs may hit Wikimedia 429s (see the rate-limit probe); run the Commons-heavy steps with backoff, or locally.
3. **Judge (one first judge)** (also checks that no neighbouring spot already has the same subject: `IMAGES.md` → "Spot photos") — only the slots the script could not prove, the audit sample and any weak slot, and **only slots that have candidates**: a search slot with an empty list goes straight to the searcher, never to a judge. The judge works from the contact sheets (one sheet of a dozen thumbnails costs about as much as two or three full images) and opens only its pick at full size; it scores the checks with reasons. A photo may be shared by one destination's header, why-visit photos and spots (the Waitomo glowworm-boat photo is all three): the searcher proposes and the judge recommends the best photo for every slot, wherever it is already used in that destination; only reuse across different destinations fails.
4. **Second judge** — re-scores, blind, only the slots where the first judge proposed a new file; disagreement means the slot stays as it is and goes to the owner. A keep-current needs no second judge (nothing changes).
   - **Scripted checks first:** `python3 scripts/curation/second-judge.py build <lens-dir>` checks every candidate of those slots for size and aspect, licence (NC, all rights reserved or none fails), a file already used by another spot, brightness and crop share, drops the failures, and draws a sheet per slot with each photo beside the crop the app shows. The judge only judges what needs eyes: right place, the thing itself, a real photograph, the subject inside the crop.
   - **Batched across groups:** the script splits the slots into batches of about 35 from any groups (`second/batch-NN.json`), one Sonnet judge per batch; `second-judge.py split <lens-dir>` merges the verdicts back into each group's `judge-2.json`. A judge's cost is mostly its fixed start: on Tonga a judge of 33 slots used 58k tokens and one of 10 used 71k.
5. **Technical check (script)** — licence, size, manifest.
6. **Report** — the final report lists, under "Photos still missing", every slot for which no passing photo was found in any tier (Commons, openly licensed, official, blogs), with the current failing photo and what was tried. Why-visit slots without a photo (grey cards, and reasons reworded or dropped for want of one) come first, and the run's closing message alerts the owner to them and asks for each photo.
Benchmark: Clyde, Hamilton, Blue Lake, the 1913 Government Gardens and the archive Blue Lake photo must all be rejected.

## Pipeline C — writing
**Every new spot goes through Pipeline C before it is applied**, whether it belongs to a new destination or an existing one. Atlas's placement entries are drafts: the proposer fills in what its sources gave, and leaves the rest empty for research, never with a placeholder. Sydney's 70 new spots were applied straight from placement, without research: 44 had no link, and spots such as Sea Life Sydney had no price. A spot is applied only when it has a cost (`free: true` or a price) and a `ticketUrl` decision: a verified link, or a stated reason for none (many operators sell it; no single steward).
0. **Tier (script)** — `scripts/curation/tier-spots.ts` sends a free, open-access place (a beach, lookout, roadside icon or monument whose name and source text show no operator, park, fee or booking) down the **simple** path: default facts (open any time, free with `costBasis: 'entry'`, a visit range by category, no link) and a bio from one batch writer for up to 40 spots, no researcher or fact-checker; one batched `fact-checker` checks every bio against its source note, and the bio still passes `lint-entries.ts` and `bio-fit.py`. Everything else, including every national park, garden, track, museum, tour, winery and anything the script is unsure of, takes the full chain below. About 12% of the simple spots (at least 3, evenly spaced) also take the full chain as an audit; if any comes back with facts different from the default (a fee, a link), the whole simple tier is rerun through the full chain.
1. **Evidence (script), then researcher** — `scripts/curation/build-evidence.ts` fetches each spot's sources once into an evidence bundle ("Lean runs"); the researcher starts from it, fetches only what it lacks, and records the facts with their source links.
   - Includes each spot's official site (`WRITING.md` → `ticketUrl`): found from the operator, loaded and checked, deep links taken from the site's own navigation. A spot with an official site and no `ticketUrl` is a failed check.
   - Includes each spot's cost: the adult price from the operator's own page, or `free: true`. Never left empty. And what the cost is for (`WRITING.md` → "What the cost is for"): `costBasis` (`entry`, `tour`, `ticket`, `park`, `donation` or `open`), `costPer` for a price not charged per adult ("Per Vehicle/Day", "Per Night"), and `needs` where a visitor must have something first (`park-pass` for a spot reached through a park pass, with `parkPass` naming it in `src/data/parkPasses.ts`; `booking`; `permit`). Every park is checked against its agency's pass list: a fee from a pass covering many parks is `park-pass`, even for a spot that is itself a park, and `park` with a price is only a park's own gate fee. Parking is never a spot's price, and a pass's price is never put on a spot (it lives once in `parkPasses.ts`, and the cost column shows it with the pass's name).
   - A site that blocks scripts is reported `BLOCKED` with its URL, not dropped: whoever runs the pipeline checks it in a real browser (the in-app browser) before the spot is applied.
2. **Writer** — several variants in the app's voice (`WRITING.md` → "Voice"). A destination's why-visit reasons are general: each reason names a kind of experience, not one of the destination's spots (Kaikōura: "Watch sperm whales year-round", "See mountains meet the sea"), except an attraction that is core or iconic to the destination, which is named (the Opera House for Sydney) (`WRITING.md` → whyVisit). The editor rewrites any that only restate a spot.
3. **Fact-checker** — every claim against the sources; cut or flag the unverifiable.
4. **Editor** — style, repetition within and across entries.
5. **Reconciler** — couple each reason (two to four, by the destination's popularity) to its photo with Pipeline B.

## The run's final report (Atlas, Lens and Quill, every run)
**Nothing a run decided on its own is left silent.** Every run, of any pipeline, ends with a report to the owner that lists each of the following by name, with the reason. A thing that is not in the report did not happen. Do not summarise these away as "a few" or "some".
- **Left out or not added**, and why: a place rejected or sent to review (with the case for and against), a spot or destination skipped for any reason (a name that collides with an existing spot, a missing price or link, a closed or no-access site, a destination not in the app, a tool limit), and anything held back. A held item says exactly what unblocks it.
- **Added or kept but weak**: a photo the judges called weak (what is wrong with it), a place kept on one counted source, a pin set from an approximate source, a price taken from a snippet, aggregator or a single old page, a bio claim that could not be re-read. Name each one and what would fix it.
- **Needs the owner**: photos still missing (a section of its own, `IMAGES.md`), official photos from sources other than tourism and parks organisations (operators, councils, businesses: permission not confirmed), links that were BLOCKED and need a real browser, new destinations the run added (to change or remove), existing spots removed, renamed or moved, and every decision the run made that the owner might want reversed.
- **Not verified**: what was not checked (a coordinate audit that was not run, a file page not opened, a price not found) and what would verify it.
Pipeline-specific items: Atlas also reports the benchmark result, the strongest candidates left out, and the standalone/inside-destination counts; Lens reports every photo slot's outcome (changed, kept, weak, none); Quill reports every spot skipped by the lint and every `ticketUrl` it could not verify.

## Cost and speed
The agents judge; scripts do everything else, and nothing is judged twice. (Wellington's first region pass used ~2.5M agent tokens, most of it on items that ended up unchanged.)
- **Scripts do the mechanical work.** `scripts/curation/score-candidates.ts` (Atlas: page views, coordinates, redirects, disambiguation pages, already-in-the-app matches), `scripts/curation/lint-entries.ts` (Quill: ticketUrl loads and names the place, paid spots without a link, spots with no cost that are not free, bio voice and length, photo titles that won't resolve, destination field counts), `scripts/photo-prefilter.ts`, `scripts/curation/lens-triage.ts` and `scripts/curation/photo-prove.py` (Lens), `scripts/curation/score-filter.ts` and `merge-verdicts.ts` (Atlas), `scripts/curation/tier-spots.ts` (Quill).
- **Triage before any agent.** Lens works only `search` and `confirm` slots (`lens-triage.ts`); Quill only the entries `lint-entries.ts` flags, or the owner names, and every new spot from Atlas (it has never been researched, so a clean lint proves nothing about it); the Atlas judge only the marginal band `score-filter.ts` leaves; Quill's simple tier gets a bio only.
- **Photo search: scripts first, agents only for the gaps.** The gather script runs the location and name searches (Commons) and Google Images (Apify, about half a cent a slot) for every slot. A searcher agent goes only to a slot the script found nothing for, or whose candidates the judge rejected.
- **Judge contact sheets, not single images**, and **skip empty slots**: a slot with no candidates costs no judge (Pipeline B step 3). In the SA headline round, 45 of 104 slots had none.
- **Second judge only on proposed changes** (Pipeline B step 4): a "none" or a keep-current gets no second look.
- **Cheaper models for mechanical roles**: `model: haiku` in `coverage-enumerator`, `image-searcher` (gaps only) and `reconciler` (staging and applying photos); `model: sonnet` in `image-judge`, because seeing what is in the photo is where quality is decided. The placing, writing and fact-checking roles keep the session's model (Sonnet).
- **Short role briefs.** Each `.claude/agents/*.md` carries a checklist of the rules its role needs; the guides stay the authority and are opened only for a case a checklist doesn't settle. Keep the checklists in step when a guide changes.
- **Cache between steps and runs.** Agents fetch pages with `npx tsx scripts/curation/fetch.ts <url>` (cache in `.cache/curation/http/`, not committed; 14 days, failures 1 day; captcha walls reported as BLOCKED), and the scripts use the same cache. Accepted photos are recorded per slot in `scripts/curation/photo-verdicts.json` (`scripts/curation/record-verdicts.ts`, or `--owner` for a photo the owner supplied); `lens-triage.ts` skips them on every later run.

**Measured on Lord Howe Island (36 candidates, 13 spots; old run vs the new stages, agent tokens):** Atlas judging 190k → 66k (recall 46k + skeptic 145k replaced by one judge; the skeptic's photo checks now sit in Lens); enumerator 124k and proposer 68k unchanged; the simple-bio writer 37k for 9 spots (old research + writing 181k for all 13; the 4 full-chain spots plus 3 audit spots are estimated at 97k, not measured); Lens unchanged (the proof cleared 1 of 13 slots: island photos are mostly un-geotagged or geotagged more than 300 m from the pin). About 19% in total on a region this small; the audit samples cost a larger share here than they will on a 150-candidate region. The big remaining costs are the enumerator and Lens's search, which these three changes do not touch.

## Lean runs (token budget)
Measured on the ACT run (46 agents; tokens weighted by price, cache reads at a tenth): about 50M, of which **half was the main session** re-reading a ~570k-token context on each of ~370 calls, 14% Quill research (agents fetching and reading whole pages, up to 93 turns each), 14% Lens searching and first judging (agents searching Commons and viewing photos one by one), and ~2.5M on reruns (a tool outage, Flickr 403s, judge reruns). The rules below target those, in that order; none changes who judges, what they judge or the bar they judge by.

- **A fresh, lean orchestrator.** A run starts in its own session (never at the end of a long one). The main session coordinates only: it runs the scripts, launches the workers, reads their short replies and the ledger, and keeps the tally. It never prints a JSON file, page text, a candidate list or an image into its own context: `python3 scripts/curation/run-ledger.py peek <file>` gives the counts, `validate <kind> <file>` checks a worker's output, `status <run-dir>` shows every stage. Scripts write to files and print one summary line.
- **Workers get paths, return summaries.** Each worker's brief names its role, its input and output paths and the rules section it needs, nothing pasted. Its reply is at most 8 lines: what it wrote, counts, and every unresolved item (the "Lean-run contract" at the end of each `.claude/agents/*.md`). Shards stay small (about 5 spots for Quill research, one destination group for Lens): an agent's cost grows with the square of its turns, since each turn re-reads the turns before it.
- **The run ledger** (`<run-dir>/run.json`, `scripts/curation/run-ledger.py`). `check` before a stage (done, with an unchanged input fingerprint, means skip it), `mark` after it, `task` per shard or group, `pending` lists the shards still to do. A failed or unresolved shard is rerun on its own; nothing finished is redone. A rerun after a usage-limit stop resumes from the ledger.
- **Unresolved is an error, not a finding.** A source blocked, rate-limited or unreachable is recorded as unresolved (evidence `unresolved`, candidates `_unresolved`, ledger `unresolved`) and retried or opened in the browser. It is never a reason to drop a place, call a photo slot empty or mark a fact unverifiable.
- **Evidence bundles for Quill** (`scripts/curation/build-evidence.ts --placement <placement.json> --out <run>/evidence`). Each spot's Atlas sources (`source_urls`, its stable id carried from placement), Wikipedia intro, official page (the cost, entry and booking lines) and the state's park-pass list, fetched once through the shared cache and cut to excerpts with URL, status and retrieval date. The researcher starts from it and fetches only what it lacks, the writer writes from it, and the fact-checker checks against it, while re-reading every price and ticketUrl fresh itself so that check stays independent.
- **Scripted photo candidates for Lens** (`scripts/curation/gather-photo-candidates.py <group-dir>`, after `lens-triage.ts` and `photo-prove.py`). Per search slot it takes the Wikipedia lead image, Commons geosearch and name searches and Google Images (one Apify call per group, results cached 30 days), applies the pre-filter in code (width for the slot type, no maps, drawings or archive dates, no near-grey scans, nothing geotagged more than 25 km from the pin), de-duplicates, ranks (lead image, then photos that name the place, nearest first), caches the thumbnails and draws a numbered contact sheet per slot plus one for the confirm slots. The first judge picks from the sheet and opens only its pick at full size with its file page; the blind second judge does the same, independently; the image-searcher (Haiku) only fills slots the script found nothing for or the judge rejected, and retries unresolved sources.
- **Models by task**: Haiku for the enumerator, the gap-only image searcher and the reconciler; Sonnet for the Atlas judge and proposer, the researcher, writer, fact-checker and editor, both image judges and the orchestrator. The copy editor is a candidate for Haiku once a side-by-side region shows no loss.
- **The run order with these rules in place** (what the expand-region skill follows; `<run>` is `curation/<branch>`):
  0. Start the run in a **fresh session** that only orchestrates. Before each stage, `run-ledger.py check <run> <stage>` (exit 0 = done, skip it); after it, `run-ledger.py mark <run> <stage> done --summary "…"`. Read worker output with `run-ledger.py peek`/`validate`, never by printing files. Workers run in waves of about ten, and a failed shard is rerun alone (`run-ledger.py pending`).
  1. **Atlas:** coverage-enumerator → `score-candidates.ts` → `score-filter.ts` → coverage-judge on the marginal band → `merge-verdicts.ts` → coverage-proposer.
  2. **Pins:** `resolve-pin.py` for every new spot.
  3. **Quill:** `build-evidence.ts --placement <placement.json> --out <run>/evidence` → `tier-spots.ts` → simple path (batch bios), or spot-researcher → copy-writer → fact-checker → copy-editor in shards of about 5 spots, each starting from the evidence bundle. No opening hours are researched or stored.
  4. **Lens:**
     1. `photo-prefilter.ts --json`, then `lens-triage.ts --region <id> --out <run>/lens --prefilter …` and `photo-prove.py <group>/task.json`.
     2. `gather-photo-candidates.py <group-dir>` for **every** search slot: name and location searches on Commons, and Google Images at the same time (needs `APIFY_TOKEN`; a failed or capped Apify call is recorded under `_unresolved` and the slot is retried on the next run).
     3. image-judge (Sonnet), first judge, on contact sheets, for groups whose slots have candidates.
     4. `build-search-queue.py <queue.json> <region> --branch <branch> --country <CC>`: every slot with no candidates, plus every first-judge reject or "none".
     5. image-searcher (Haiku) on that queue only, then the first judge on what it found.
     6. `second-judge.py build <lens-dir>` (scripted checks, batches of about 35 across groups), then one blind second judge (Sonnet) per batch on proposed changes only, then `second-judge.py split <lens-dir>`.
     7. reconciler (Haiku) stages, links and applies.
  5. **Apply and verify** as in "Applying edits to `src/data`".
- **Expected effect** (ACT as the baseline, savings not double-counted): the lean orchestrator about 40% of the run (main session ~25M → ~5M), evidence bundles and smaller Quill shards about 7%, scripted photo candidates and sheet-based judging about 7%, the Haiku image searcher about 2%, no full reruns about 3–5%. Together roughly 55–60%, to be confirmed by measuring the next region (`run-ledger.py status` plus the agents' transcripts).

## Build order
Pipeline B first (most objective checks), then A, then C.

## What is implemented
- **Scripts (deterministic):** the `scripts/curation/` tools in "Cost and speed"; `scripts/photo-prefilter.ts` (Pipeline B step 1 and the technical check; hard fails plus colour "review" flags, cached per file in `scripts/prefilter-cache.json`) and `scripts/curation-backlog.ts` (weakest-first ranking and the next batch of 5). Existing: `check-destination-headers.ts`, `audit-spot-coordinates.ts`, `build-image-manifest.ts`.
- **Roles:** one subagent per role in `.claude/agents/` (`image-searcher`, `image-judge`, `coverage-enumerator`, `coverage-judge`, `coverage-proposer`, `spot-researcher`, `copy-writer`, `fact-checker`, `copy-editor`, `reconciler`). They point at the guides and add no rules of their own.
- **Orchestration:** one prompt per pipeline in `.claude/routines/` (`b-imagery.md`, `a-coverage.md`, `c-writing.md`). A cloud routine's prompt is just "follow `.claude/routines/<file>`", so changing a pipeline is a normal pull request.
- **Pre-filter findings are inputs, not verdicts.** A hard fail is objective (an archive date, a map or flag category, too small, one photo used for two different destinations); a few can be false positives (a flags category on a Times Square photo), so the judges look at them. "Review" flags are colour heuristics that a sunset can trip.

## Running the pipelines (lessons from the New Zealand run)
- **Where the prompts and helpers live:** per-job prompts in `.claude/routines/jobs/` (`job-first.md` and `job-second.md` for imagery; `jobA-region.md`, `jobA-judge.md` and `jobA-place.md` for coverage. The per-destination and country-level coverage prompts used in the first New Zealand run were retired: they searched destinations far harder than the land between them), search helper `scripts/commons-candidates.py`, and the appliers below. Each destination's evidence is written to `curation/<branch>/<destination>/` and committed, so a rerun skips what is finished.
- **Rate limits are the main failure.** Wikimedia answers 429 in bursts, and Nominatim and Overpass refuse or time out when several agents share an IP; Overpass was unusable. Agents should pace requests (about 1 per second), back off on 429, and fall back to the Wikipedia coordinates API and Commons geotags. The cloud environment's shared IP is throttled harder than a home connection (see the rate-limit probe), so run the Wikimedia-heavy steps locally.
- **A usage-limit stop kills every running agent at once.** Launch in waves of about ten, not all at once, and make each stage resumable from the files it already wrote.
- **A "none" from the first judge needs no second judge** (nothing to re-score); a finalist always does. Where the two judges pick different files, use one both accepted.
- **A missing photo never blocks a spot or destination.** The photo search must try every tier, Commons then non-Commons, before giving up. If no passing photo exists, the spot or destination is still added, and the run's final report asks the owner to provide a photo for it ("Photos still missing"). Nothing is held back or dropped for want of a photo.
- **Applying edits to `src/data`:** one writer, one commit per destination. For a region: `scripts/curation/build-apply-placement.py <region-id>` (flat placement from Quill's final copy and the skeptic's photo candidates), then `scripts/curation/apply-region.py <region-id> [--dry-run]`, which works for any country and branch (the evidence folder is found under `curation/*/region-<id>/`; the country, currency and timezone come from `scripts/coverage-regions.json` and `COUNTRY_DEFAULTS` in the script: **add a new country there before its first run**, and a region's own `timezone` where it differs, as Tasmania's does). It adds only spots with researched copy, an accepted photo and a real pin, and lists everything else with the reason. A new destination goes in with `scripts/curation/apply-destination.py`, its spots after it. Always `--dry-run` first; rebuild the manifest (`scripts/build-image-manifest.ts`), then run `tsc`, the header check, `scripts/photo-prefilter.ts` and `scripts/audit-spot-coordinates.ts`. The audit's "in water" flags are often a beach or lake edge, so move the point onto land with a Mapbox tilequery rather than trusting a rounded coordinate.
- **Stricter bar, review list.** The judge keeps only what passes `COVERAGE.md` → "What qualifies"; marginal places go to a review list in the pull request for the owner (weekly markets, festivals and exterior-only civic buildings never qualify).
