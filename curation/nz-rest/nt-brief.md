# Brief: NT shard (pins + facts + copy), shared by all shard agents

Repo: /Users/alexzhou/Developer/mobile-wellington (run commands from there). Read WRITING.md (names, spot fields, destination fields, voice) and COVERAGE.md "Verifying coordinates" before you start. Do NOT edit src/ or any file except your own output files. Do not run git.

Input: your shard's ids/names (in your prompt) and the region's `curation/nz-rest/region-<region>/placement.json` (draft entries: icon, category, bio, wiki, provisional coordinates, sources, needs_research; destinations under new_destinations with name_evidence). Approved by the owner: all proposed destinations as proposed (id, name, category, rank, span in the placement). Review-list places are NOT included; never add or raise them.

For every spot in your shard produce a finished entry (shape of curation/nz-rest/quill/nt-darwin-top-end/final.json `spots`):
`{ name, icon, category, bio, hours, visitHoursMin, visitHoursMax, coordinates: {latitude, longitude}, wiki (only if the Wikipedia article title differs from name; else omit/null), free: true | costMin/costMax/currency 'AUD', ticketUrl, coordinates_source, notes }`

1. PIN: `python3 scripts/curation/resolve-pin.py --name "<spot>" --category <category> --lat <hint> --lon <hint> [--wiki "<title>"]` (a call can take ~2 min; run several in the background with `&` and wait, or use targeted Overpass queries via curl). Use a HIGH or MEDIUM point only. Rules (COVERAGE.md): a park at its visitor point (visitor centre, day-use area, main lookout/car park; never the centroid, never a point shared with another spot); a town at its OSM place=town/village centre; a walk/track at the midpoint of the whole OSM route (resolve-pin reports it); a summit/lookout on the feature; a waterhole/gorge/falls at the feature or its car park. Every spot must be >=25 m from every other spot's and its destination's pin (check against src/data/spots.ts, src/data/destinations.ts and the other entries in your shard). Never memory, never a 3-decimal-or-fewer point, never a town page point. If only LOW: use the managing agency's trailhead/car park point from a source and say so in coordinates_source, or mark `"pin": "LOW"` in notes so I raise it. Record the source and feature type in coordinates_source.
2. FACTS: hours, cost (free:true or AUD price; NT Parks Visitor Pass applies only where the park page states a fee), official ticketUrl, visit hours range (quarter-hour steps, WRITING.md). Sources: official operator/agency pages, Wikivoyage, Parks Australia, northernterritory.com. nt.gov.au / Parks and Wildlife NT pages block scripts (403/Cloudflare): use WebSearch snippets, and list every ticketUrl you could not load in your notes under `needs_browser` with the URL so I can verify it in the in-app browser. Never guess a domain. Never invent: if hours cannot be sourced, give a short honest qualifier ("Daily, seasonal; check closures" is NOT acceptable as a placeholder; use e.g. `Open 24 hours` for open-access places, or the sourced range) and list the item under `unverified` in notes. Seasonal/wet-season closures go into the bio only if they fit, otherwise into notes.
3. BIO: one sentence, >=10 words, fits three card lines (<=~120 chars; check `python3 scripts/curation/bio-fit.py --text "<bio>"`), what it is, where, the one thing that makes it worth a stop; no source names, no superlatives you cannot back; fix errors in the draft bio (e.g. Anmatjere Man is 17 m per NT tourism, not 12).
4. Names: the place's own name, title case, no qualifiers. A spot's `wiki` is the exact Wikipedia article title only if different from name AND the article is about that place (not a broader article it redirects to).
5. DESTINATIONS in your shard (listed in your prompt): write `{ destination: { id, name, country:'Australia', countryCode:'AU', timezone:'Australia/Darwin', continent:'Oceania', coordinates (the visitor hub / town centre / park visitor point from resolve-pin, not a centroid, not any spot's pin), category, defaultZoomSpanKm (check every spot lies within 75% of it), rank, icon, tagline, description (3-4 sentences), whyVisit (2-4 by rank: 4 for rank 1-2, 3 for rank 3-4, 2 for rank 5; each 2-8 words starting with an action verb), highlights (one 2-3 word phrase per reason), goodToKnow (2-3: 3 for rank 1-3, 2 for rank 4-5; icon, title 2-5 words, detail <=160 chars), bestMonths, bestTimeBlurb (one {months}), seasonalTags? }, spots: [ids in importance order], notes }` — see curation/nz-rest/quill/nt-darwin-top-end/dest-litchfield.final.json. The destination's spots must be listed in importance order (the headline first); if the order in the placement is wrong, say so and give the new order (ids stay).
6. Voice: facts from sources only, never name a source in copy, concrete, not marketing; no repetition between description, reasons and tips.

OUTPUT: write `curation/nz-rest/quill/<region>/<shard>.json` = `{ "spots": { "<id>": {...}, ... }, "destinations": [ { destination..., spots:[...], notes } ], "unverified": [...], "needs_browser": [ {id, url, why} ], "notes": [...] }`. Validate it parses (`python3 -c "import json;json.load(open(path))"`). Final message: counts, every unverified/LOW/needs_browser item by name, and anything you judged should not be added (with why).
